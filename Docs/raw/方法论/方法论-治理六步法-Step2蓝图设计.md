# Step 2：蓝图设计（Week 3-4）

## 📌 目标
基于调研结果，设计数据治理的总体架构、组织机制、标准框架和实施路线图。

## 📋 详细过程

### 2.1 调研结果分析（第1-2天）

**分析内容**：
- 梳理所有调研发现，按主题分类（组织/制度/标准/质量/安全/工具）
- 识别关键矛盾和冲突（如业务部门诉求 vs 技术部门能力）
- 评估各改进项的依赖关系（哪些必须先做，哪些可以并行）
- 初步估算各改进项的工作量和难度

**输出**：《调研发现分析表》

| 发现编号 | 发现内容 | 所属领域 | 严重程度 | 改进建议 | 依赖项 | 工作量 |
|:-------:|:--------|:-------|:-------:|:--------|:------|:------|
| F001 | 85%字段无Owner | 认责 | 高 | 建立字段级认责体系 | 无 | 中 |
| F002 | EAST报送返工3次/季 | 质量 | 高 | 统一监管报送口径 | F001 | 高 |

### 2.2 治理组织架构设计（第2-4天）

**设计内容**：

#### 2.2.1 三层治理架构

```
┌─────────────────────────────────────────┐
│  第一层：战略决策层                       │
│  数据治理委员会                           │
│  • 组成：CEO/CTO/CDO + 各业务部门负责人   │
│  • 职责：审批数据战略、协调重大冲突        │
│  • 频率：每季度1次                        │
└─────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────┐
│  第二层：管理推进层                       │
│  数据治理办公室/数据管理部                 │
│  • 组成：数据治理经理 + 治理专员          │
│  • 职责：制定标准、推动落地、监控质量      │
│  • 频率：每周1次例会                      │
└─────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────┐
│  第三层：执行落实层                       │
│  数据Owner + 数据Steward + 数据Custodian  │
│  • Owner：业务部门负责人，定规则           │
│  • Steward：业务骨干，日常管理             │
│  • Custodian：技术人员，技术实施           │
│  • 频率：按需，问题驱动                    │
└─────────────────────────────────────────┘
```

#### 2.2.2 RACI矩阵设计

为每个关键数据管理活动设计RACI矩阵（见总览部分的RACI表）。

**关键设计原则**：
- 每个活动必须有且只有一个A（Accountable）
- Owner必须是业务方（不能全是IT或数据团队）
- Steward是Owner指定的执行人，负责日常对接

### 2.3 制度体系框架设计（第3-5天）

**制度体系框架**：

```
数据治理制度体系
│
├── 纲领层（1个）
│   └── 《数据治理管理办法》
│       └── 定位：数据治理的纲领性文件
│       └── 内容：目标、原则、组织架构、职责分工、考核机制
│
├── 规范层（3-5个）
│   ├── 《数据标准管理办法》
│   ├── 《数据质量管理办法》
│   ├── 《数据安全管理办法》
│   ├── 《元数据管理办法》
│   └── 《数据生命周期管理办法》
│
└── 操作层（N个）
    ├── 《数据标准制定流程》
    ├── 《数据质量问题处理流程》
    ├── 《数据变更管理流程》
    ├── 《数据需求管理流程》
    └── ...
```

**设计原则**：
- 先设计框架，不急于写完整内容
- 制度要可执行，不要写空话
- 每个制度明确：适用范围、责任人、执行流程、考核方式

---

### 2.4 数据标准框架设计（第4-6天）

**标准体系框架**：

```
数据标准体系
│
├── 基础标准
│   ├── 业务术语标准（统一业务语言）
│   ├── 数据元标准（字段级定义）
│   └── 编码规范（命名规则）
│
├── 业务标准
│   ├── 参考数据标准（枚举值：证件类型、学历等）
│   ├── 主数据标准（客户、产品、机构）
│   └── 指标数据标准（口径统一的业务指标）
│
└── 技术标准
    ├── 数据模型规范
    ├── 接口规范
    └── 交换格式规范
```

**设计原则**：
- 先定"哪些领域需要标准"，再定"每个标准的具体内容"
- 标准制定优先级：高频使用 > 问题严重 > 监管要求 > 其他
- 第一批标准控制在5-10个，不要贪多

### 2.5 实施路线图设计（第6-8天）

**路线图要素**：

| 要素 | 内容 |
|:-----|:-----|
| 阶段划分 | 分几个阶段？每个阶段的目标是什么？ |
| 时间计划 | 每阶段的起止时间、里程碑 |
| 优先级排序 | 哪些先做？哪些后做？为什么？ |
| 资源需求 | 人力、资金、工具 |
| 依赖关系 | 哪些任务有先后顺序？ |
| 风险预判 | 每个阶段的主要风险是什么？ |

**优先级排序方法**：

使用"影响-难度"矩阵：

```
        高影响
          │
    快速赢 │ 战略重点
    (先做) │ (规划好再做)
          │
低难度 ───┼─────── 高难度
          │
    低优先级│ 必要基础
    (最后做) │ (拆解后做)
          │
        低影响
```

- 高影响+低难度 = 快速赢，先做（Quick Win）
- 高影响+高难度 = 战略重点，规划好再做
- 低影响+低难度 = 有空再做
- 低影响+高难度 = 最后做或不做

### 2.6 蓝图方案评审（第9-14天）

**评审流程**：
1. 内部预审（数据治理团队内部）
2. 发起人审阅（项目发起人过目）
3. 正式评审会（数据治理委员会）
4. 根据评审意见修改
5. 正式发布

**评审会材料**：
- 蓝图方案报告（Word）
- 汇报PPT（15页）
- 相关附件（组织架构图、路线图甘特图、RACI矩阵）

### 交付物6：《数据治理实施路线图》★ 核心交付物

**内容**：

```
一、总体策略
   1.1 实施原则（先试点再推广、先治标再治本等）
   1.2 阶段划分（通常3-4个阶段）
   1.3 总体时间表

二、第一阶段详细计划（试点阶段）
   2.1 目标
   2.2 范围（选哪个领域/系统试点）
   2.3 任务分解（WBS）
   2.4 时间安排（甘特图）
   2.5 资源需求
   2.6 成功标准
   2.7 风险与应对

三、第二阶段计划（推广阶段）
   ...（同上结构，概要级）

四、第三阶段计划（深化阶段）
   ...（同上结构，概要级）

五、资源总需求
   5.1 人力需求（角色、数量、时间）
   5.2 资金需求（工具采购、咨询费用等）
   5.3 工具需求

六、风险管理
   6.1 风险清单
   6.2 应对策略
   6.3 应急预案
```

**格式**：Word报告 + Excel甘特图 + PPT汇报版

**关键要求**：
- 甘特图要精确到周
- 标注里程碑和评审点
- 标注任务依赖关系（哪些任务必须先完成）
- 资源需求要具体（不要只写"需要人力"，要写"需要1名数据质量工程师，全职3个月"）

## 💡 Step 2 关键技巧

| 技巧 | 说明 |
|:-----|:-----|
| 组织架构要实际 | 不要为了好看设一堆虚职，要考虑现有人力 |
| 制度先搭框架 | 不要一开始就写完整制度，先定框架再逐步填充 |
| 标准要聚焦 | 第一批标准控制在5-10个，选高频+高问题领域 |
| 路线要留buffer | 时间表留20%缓冲，数据治理项目经常延期 |
| 评审前私下沟通 | 正式评审前先跟关键干系人一对一沟通，争取支持 |
| 用Quick Win建信心 | 第一阶段一定要选能快速出成果的领域 |

## ⚠️ Step 2 常见坑

| 坑         | 后果                     | 如何避免                 |
| :-------- | :--------------------- | :------------------- |
| 组织架构设计太理想 | 找不到合适的人担任Owner/Steward | 基于现有人力设计，先兼职后专职      |
| 制度写得像法律条文 | 看不懂，执行不了               | 用流程图+表单+示例说明，少写原则性文字 |
| 标准范围定太大   | 制定不完，执行不了              | 聚焦核心领域，小步快跑          |
| 路线图太激进    | 按期完不成，打击信心             | 保守估算时间，留buffer       |
| 忽略技术可行性   | 方案很好但技术实现不了            | 设计时让技术团队参与评审         |
| 没有量化收益    | 领导看不到价值，不给资源           | 每个改进项都要有量化收益估算       |
