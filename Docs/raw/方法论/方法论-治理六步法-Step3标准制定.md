# Step 3：标准制定（Week 5-8）

## 📌 目标
制定第一批数据标准，建立标准管理流程，确保标准可被理解和执行。

## 📋 详细过程

### 3.1 确定第一批标准清单（第1天）

**选择标准的原则**：
1. 高频使用：每天都在用的数据
2. 问题严重：数据质量问题多的领域
3. 监管要求：涉及EAST/1104报送的字段
4. 跨系统使用：多个系统共享的数据
5. 技术可行：能在现有系统条件下落地

**标准清单模板**：

| 标准编号 | 标准名称 | 标准类型 | 适用范围 | 优先级 | 责任人 | 计划完成时间 |
|:-------:|:--------|:-------|:-------|:------:|:-----:|:-----------:|
| STD-001 | 客户信息数据标准 | 主数据 | 全公司 | P0 | 零售部 | Week 6 |
| STD-002 | 贷款产品数据标准 | 参考数据 | 信贷系统 | P0 | 产品部 | Week 7 |
| STD-003 | 还款状态编码标准 | 参考数据 | 核心/信贷 | P1 | 运营部 | Week 8 |

---

### 3.2 组建标准制定小组（第1-2天）

**小组构成**：
- 组长：数据治理团队人员（协调推进）
- 业务代表：Owner部门骨干（定义业务含义）
- 技术代表：IT开发人员（评估技术可行性）
- 数据代表：数据分析师（确认口径和用法）

**每个标准一个小组**，不要一个大组做所有标准。

---

### 3.3 标准内容起草（第2-6天）

**标准内容模板**（以客户信息标准为例）：

```
《客户信息数据标准 V1.0》

一、标准目的
   统一全公司客户信息的定义、格式和使用规范

二、适用范围
   适用于所有涉及客户信息的业务系统和数据平台

三、术语定义
   3.1 客户：与本公司发生业务关系的个人或机构
   3.2 自然人客户：以个人身份办理业务的客户
   3.3 机构客户：以企业/组织身份办理业务的客户

四、数据元标准（核心内容）

   ┌─────────────┬─────────────┬──────────┬────────┬────────┬────────┬────────┐
   │ 标准字段名   │ 业务含义     │ 数据类型  │ 长度   │ 必填   │ 默认值 │ 取值范围│
   ├─────────────┼─────────────┼──────────┼────────┼────────┼────────┼────────┤
   │ customer_id  │ 客户唯一标识 │ 字符串   │ 32     │ 是     │ 无     │ UUID   │
   │ customer_name│ 客户姓名     │ 字符串   │ 50     │ 是     │ 无     │ -      │
   │ id_type      │ 证件类型     │ 枚举     │ 2      │ 是     │ 无     │ 01身份证│
   │              │              │          │        │        │        │ 02护照  │
   │ id_no        │ 证件号码     │ 字符串   │ 18     │ 是     │ 无     │ -      │
   │ mobile       │ 手机号       │ 字符串   │ 11     │ 是     │ 无     │ 符合   │
   │              │              │          │        │        │        │ 手机号  │
   │              │              │          │        │        │        │ 正则    │
   │ gender       │ 性别         │ 枚举     │ 1      │ 否     │ 9      │ 0女    │
   │              │              │          │        │        │        │ 1男    │
   │              │              │          │        │        │        │ 9未知  │
   │ birthday     │ 出生日期     │ 日期     │ -      │ 否     │ 无     │ -      │
   │ credit_level │ 信用等级     │ 枚举     │ 1      │ 否     │ C      │ A/B/C/D│
   │ create_time  │ 创建时间     │ 日期时间 │ -      │ 是     │ 无     │ -      │
   │ update_time  │ 更新时间     │ 日期时间 │ -      │ 是     │ 无     │ -      │
   └─────────────┴─────────────┴──────────┴────────┴────────┴────────┴────────┘

五、编码规则
   5.1 客户号生成规则：UUID，全局唯一
   5.2 证件号码校验规则：身份证按GB 11643校验
   5.3 手机号校验规则：正则 ^1[3-9]\d{9}$

六、质量标准
   6.1 完整性：customer_id, customer_name, id_type, id_no, mobile 非空率100%
   6.2 准确性：mobile格式合规率100%，id_no格式合规率100%
   6.3 唯一性：customer_id 全局唯一，id_no+id_type 联合唯一

七、Owner与Steward
   7.1 Owner：零售业务部总监
   7.2 Steward：零售业务部数据管理员（张三）

八、变更管理
   8.1 标准变更需经Owner审批
   8.2 变更需评估对下游系统的影响
   8.3 变更需提前2周通知相关方

九、附则
   9.1 本标准自发布之日起生效
   9.2 解释权归数据治理办公室
```

**起草要点**：
- 每个字段必须有明确的业务含义（用业务语言，不是技术语言）
- 必须有质量标准和检核规则
- 必须明确Owner和Steward
- 必须有变更管理流程

### 3.4 跨部门评审（第6-10天）

**评审流程**：
1. 标准初稿发给相关方预审（2天）
2. 收集反馈意见（1天）
3. 召开评审会（半天）
4. 根据评审意见修改（1-2天）
5. 终稿确认（1天）

**评审会参与人**：
- 标准Owner（必须到场，有决策权）
- 使用该标准的业务部门代表
- 相关系统的技术负责人
- 数据治理团队

**评审检查清单**：

| 检查项 | 通过标准 | 检查人 |
|:------|:--------|:-----:|
| 业务含义清晰 | 非技术人员能看懂 | 业务代表 |
| 技术可行 | 现有系统能支持 | 技术代表 |
| 无冲突 | 不与已有标准矛盾 | 数据治理 |
| 完整 | 包含质量标准和Owner | 数据治理 |
| 可执行 | 有明确的实施计划 | 全体 |

---

### 3.5 标准发布（第10-14天）

**发布流程**：
1. 标准终稿提交Owner签字
2. 数据治理办公室审核格式
3. 正式发布（邮件+OA系统归档）
4. 通知相关方（邮件抄送所有利益相关方）
5. 纳入元数据管理平台（如有）

**发布通知模板**：

```
主题：【正式发布】《客户信息数据标准V1.0》

各位同事：

《客户信息数据标准V1.0》已通过评审，现正式发布。

【标准要点】
- 统一了全公司客户信息的字段定义和格式
- 核心字段：customer_id, customer_name, id_type, id_no, mobile等
- 质量标准：关键字段非空率100%，格式合规率100%

【Owner与Steward】
- Owner：零售业务部 张总
- Steward：零售业务部 张三

【实施要求】
- 新建系统：按新标准执行
- 已有系统：详见《落标实施计划》

【反馈渠道】
如对标准有疑问，请联系Steward张三（zhangsan@company.com）

数据治理办公室
2025年X月X日
```

## 💡 Step 3 关键技巧

| 技巧 | 说明 |
|:-----|:-----|
| 先定框架再填内容 | 先把所有标准的模板定好，再逐一填充 |
| 业务语言写标准 | 不要用技术术语，要让业务人员看得懂 |
| 每个标准必须有Owner签字 | 没有Owner签字的标准等于没发布 |
| 标准要可度量 | 每个标准必须有明确的质量检核规则 |
| 评审会前私下沟通 | 正式评审前跟各方确认意见，避免会上扯皮 |
| 发布时广而告之 | 不要默默发布，要让所有相关方知道 |

## ⚠️ Step 3 常见坑

| 坑 | 后果 | 如何避免 |
|:--|:-----|:--------|
| 标准定义模糊 | 执行时各理解各的 | 用"是/否"、枚举值、正则表达式等精确描述 |
| 忽略历史数据 | 新标准无法适配存量数据 | 标准里必须包含历史数据处置方案 |
| 没有技术评审 | 标准定好了但系统改不了 | 标准评审必须有技术代表参与 |
| 标准太多太细 | 制定不完，执行不了 | 第一批控制在5-10个标准 |
| 标准Owner不认账 | 签了字但不执行 | 签字前充分沟通，明确职责边界 |
| 发布后就不管了 | 标准成了摆设 | 建立定期评审机制（每季度/半年） |
