# Step 5：质量监控（Week 17-20）

## 📌 目标
建立常态化的数据质量监控机制，确保标准被持续执行，问题被及时发现和闭环。

## 📋 详细过程

### 5.1 设计质量监控体系（第1-3天）

**监控体系框架**：

```
数据质量监控体系
│
├── 检核规则层
│   ├── 完整性规则（非空、非空字符串）
│   ├── 准确性规则（格式、范围、枚举）
│   ├── 一致性规则（跨系统比对）
│   ├── 及时性规则（更新延迟）
│   └── 唯一性规则（主键重复）
│
├── 监控执行层
│   ├── 自动化检核（每日/每小时跑批）
│   ├── 人工抽查（每月抽样）
│   └── 业务反馈（随时）
│
├── 问题处理层
│   ├── 问题发现 → 自动告警
│   ├── 问题分发 → 通知Steward
│   ├── 问题处理 → Steward整改
│   ├── 问题验证 → 治理团队复核
│   └── 问题归档 → 记录台账
│
└── 报告展示层
    ├── 实时质量看板
    ├── 日报/周报/月报
    └── 质量考核通报
```

### 5.3 建立问题闭环流程（第4-8天）

**闭环流程**：

```
检核规则触发
    │
    ▼
自动告警（邮件/短信/企业微信）
    │
    ▼
通知 Steward（2小时内响应）
    │
    ▼
Steward 定位原因（24小时内）
    │
    ▼
Steward 制定整改方案（48小时内）
    │
    ▼
执行整改
    │
    ▼
治理团队验证（整改后下次跑批）
    │
    ▼
验证通过 → 归档
验证不通过 → 重新整改
```

### 5.4 设计质量报告（第6-10天）

**日报内容**（自动发送）：
- 今日检核规则执行数
- 通过数/失败数
- 新增问题数
- TOP 3问题

**周报内容**（自动生成）：
- 本周质量得分趋势
- 各域质量得分排名
- 问题闭环情况（新增/已解决/超期）
- 下周关注重点

**月报内容**（人工整理）：
- 月度质量总体评价
- 各系统/各域质量得分
- 问题根因分析
- 改进建议

### 5.5 建立考核机制（第8-14天）

**考核指标设计**：

| 考核对象 | 考核指标 | 权重 | 数据来源 |
|:-------|:--------|:----:|:--------|
| 数据Owner | 负责字段的质量得分 | 40% | 质量监控平台 |
| | 问题响应时效 | 20% | 问题台账 |
| | 问题闭环率 | 20% | 问题台账 |
| | 标准执行率 | 20% | 映射文档 |
| 数据Steward | 问题处理时效 | 50% | 问题台账 |
| | 问题处理质量 | 30% | 验证结果 |
| | 数据质量提升率 | 20% | 月度对比 |

**考核周期**：月度评分，季度通报，年度汇总

**考核结果应用**：
- 与绩效奖金挂钩（建议占比5-10%）
- 与评优评先挂钩
- 质量得分排名公示（正向激励）

## 💡 Step 5 关键技巧

| 技巧 | 说明 |
|:-----|:-----|
| 规则由少到多 | 先配核心规则的10条，逐步增加 |
| 阈值由松到紧 | 先设90%，逐步提升到95%、99% |
| 告警分级 | 严重问题立即通知，警告问题日报汇总 |
| 问题不过夜 | 严重问题当天响应，避免积累 |
| 定期复盘 | 每周 review 问题台账，分析趋势 |
| 正向激励 | 质量得分排名公示，奖励进步大的部门 |

## ⚠️ Step 5 常见坑

| 坑 | 后果 | 如何避免 |
|:--|:-----|:--------|
| 规则配太多 | 告警泛滥，没人看 | 先配核心规则的10条，逐步增加 |
| 阈值太严格 | 误报太多，失去信任 | 根据历史数据设定合理阈值 |
| 只发告警不跟进 | 问题永远在那 | 建立闭环流程，每个问题必须有关闭记录 |
| 考核太重 | 业务部门抵触 | 占比控制在5-10%，以激励为主 |
| 报告没人看 | 监控成了摆设 | 报告要简洁，突出TOP问题，直接推给责任人 |
