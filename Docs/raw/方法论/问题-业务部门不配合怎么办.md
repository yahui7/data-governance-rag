# 问题：业务部门不配合怎么办

## ❓ 问题描述

业务部门拒绝担任数据Owner，或拒绝配合标准落地。常见借口：
- "这不是我们的数据"
- "我们很忙，没空管这个"
- "改了会影响现有业务"
- "以前一直这样做的，为什么要改"

## 🔍 根因分析

| 表面原因 | 深层原因 | 根因 |
|:--------|:--------|:-----|
| "这不是我们的数据" | 怕担责，担心增加工作量 | 不了解Owner职责边界 |
| "我们很忙" | 看不到数据治理的价值 | 没有量化的收益展示 |
| "会影响业务" | 对变更的影响不确定 | 缺乏充分的沟通和培训 |
| "以前一直这样" | 改变习惯有成本 | 没有足够的外部压力或激励 |

## 💡 解决方案

### 策略A：用事实说话

**核心逻辑**：让业务部门看到"不改"的损失和"改"的收益

**话术**：
> "因为这个字段不准确，上季度监管报送返工3次，每次返工需要20人时。如果监管问责，没有明确Owner的问题，领导会问业务部门负责人。"

**数据准备**：
- 质量问题造成的损失（人工耗时、返工成本、处罚风险）
- 同行业案例（其他公司因数据问题被处罚的案例）
- 监管趋势（监管对数据质量的要求越来越高）

### 策略B：降低门槛

**核心逻辑**：让业务部门知道"认责不等于增加大量工作"

**话术**：
> "认责不是让您额外做很多工作。日常监控由数据团队做，您只需要在业务含义变更时确认、质量问题严重时配合处理即可。"

**具体措施**：
- 数据团队做"脏活累活"（监控、分析、提方案）
- Owner只需要"确认"和"拍板"
- 提供一站式服务，不要让Owner到处找人
- Steward代劳日常事务

### 策略C：从领导层推动

**核心逻辑**：用组织权威解决阻力

**具体措施**：
- 在数据治理委员会上讨论认责方案
- 由公司高层（CTO/CDO）拍板
- 发布正式文件，明确认责结果
- 将认责情况纳入部门考核

### 策略D：先易后难，树立标杆

**核心逻辑**：用成功案例带动其他部门

**具体措施**：
- 找一个配合度高的部门先做试点
- 做出成果后展示给其他部门看
- "XX部门认了责之后，他们的数据质量得分从60提升到90"
- 给予试点部门额外资源或表彰

## ✅ 推荐组合拳

**对于一般抵触**：策略A + 策略B
**对于强烈抵触**：策略A + 策略B + 策略C
**对于观望态度**：策略D

## 📋 话术模板（可直接使用）

```
"我理解您的顾虑。让我澄清一下：

第一，这个字段的业务含义是由贵部门制定的，其他部门只是使用。
按'谁产生、谁定义、谁负责'的原则，业务含义的最终解释权在贵部门。

第二，认责不是让您额外做很多工作。日常监控由数据团队做，
您只需要在业务含义变更时确认、质量问题严重时配合处理即可。

第三，如果确实不是贵部门的，那我们一起看看谁更适合做Owner，
在治理委员会上讨论确定。

您看这样可以吗？"
```

## 🔄 预防措施

- 认责前充分沟通，解释Owner职责边界
- 准备FAQ文档，回答常见顾虑
- 高层在治理委员会上明确支持
- 将认责结果正式发文，减少后续争议
