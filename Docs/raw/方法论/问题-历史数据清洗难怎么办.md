# 问题：历史数据清洗难怎么办

## ❓ 问题描述

历史数据质量太差，清洗工作量大、规则难制定、业务不敢确认。

## 🔍 根因分析

| 难点 | 原因 |
|:-----|:-----|
| 工作量大 | 历史数据量大（百万/千万级），全量清洗耗时耗力 |
| 规则难定 | 历史数据问题多样，同一问题可能有多种处理方式 |
| 业务不敢确认 | 怕担责，不敢对历史数据的处理结果签字 |
| 清洗后可能出错 | 担心清洗脚本有bug，把数据洗坏 |

## 💡 解决方案

### 策略1：先定规则再清洗

**核心原则**：规则必须经业务方确认，技术团队只执行

**步骤**：
1. 数据治理团队提出清洗规则建议
2. 业务Owner审核确认
3. 清洗结果抽样给业务方复核
4. 最终确认后大批量执行

**清洗规则表示例**：

| 字段 | 问题类型 | 问题示例 | 清洗规则 | 清洗后 | 验证方法 | 业务确认 |
|:-----|:--------|:--------|:--------|:------|:--------|:-------:|
| mobile | 格式不规范 | 138-0013-8000 | 去除所有非数字字符 | 13800138000 | 正则校验 | ✓ |
| mobile | 带前缀 | +8613012345678 | 去除+86前缀 | 13012345678 | 长度=11 | ✓ |
| id_type | 编码不一致 | 身份证/ID/01 | 统一映射为01 | 01 | 枚举值校验 | ✓ |
| customer_name | 有空格 | " 张三 " | 去除首尾空格 | "张三" | 长度对比 | ✓ |

### 策略2：分批次执行

**核心原则**：不要一次性清洗全部数据，分批降低风险

**分批策略**：

| 批次 | 范围 | 数量 | 目的 |
|:-----|:-----|:-----|:-----|
| 第0批 | 测试环境100条 | 100 | 验证清洗脚本正确性 |
| 第1批 | 最近1个月数据 | 1万 | 验证清洗规则合理性 |
| 第2批 | 最近6个月数据 | 10万 | 小批量验证 |
| 第3批 | 最近1年数据 | 50万 | 中批量验证 |
| 第4批 | 剩余全部数据 | 其余 | 大批量执行 |

### 策略3：保留备份

**核心原则**：清洗前必须备份，万一出错可以回滚

**备份要求**：
- 全量备份待清洗的表
- 备份保留至少30天
- 保留清洗前后的对照关系
- 清洗脚本和日志归档

### 策略4：脏数据分类处理

**不同问题，不同处理方式**：

| 数据类型 | 处理方式 | 示例 |
|:--------|:--------|:-----|
| 格式问题 | 自动清洗 | 去除空格、横线、+86前缀 |
| 缺失值 | 能补则补，不能补标记 | 补全为"未知"或留空 |
| 明显错误 | 标记为待核实，不自动改 | 手机号少一位 |
| 无法判断 | 保留原值，记录问题 | 地址信息无法判断对错 |
| 重复数据 | 按规则合并或标记 | 同一客户多条记录 |

## ✅ 推荐清洗流程

```
Step 1：备份原始数据（保留30天）
    ↓
Step 2：制定清洗规则（业务Owner确认）
    ↓
Step 3：小批量测试（100条→1万条）
    ↓
Step 4：业务方确认清洗结果
    ↓
Step 5：大批量执行（分批，每批验证）
    ↓
Step 6：全量验证（统计+抽样人工复核）
    ↓
Step 7：归档（脚本、日志、验证结果）
```

## 📋 话术模板（可直接使用）

**场景：业务方不敢确认清洗规则**
```
"我理解您的担心。我们这样处理：

第一步，我们先准备清洗规则建议，请您审核，您觉得不合理的我们可以调整。

第二步，我们只在测试环境先洗100条，您看看结果对不对。

第三步，如果100条没问题，我们再洗1万条，您再抽查看看。

第四步，您确认没问题了，我们再大批量执行。

每一步都有备份，万一出问题可以回滚。您看这样可以吗？"
```

## 🔄 预防措施

- 新标准实施时，同时在新旧系统保留字段，便于对照
- 建立数据清洗审批流程，清洗前必须Owner签字
- 清洗脚本必须经过代码评审
- 建立清洗结果抽查机制（至少抽查1%）
