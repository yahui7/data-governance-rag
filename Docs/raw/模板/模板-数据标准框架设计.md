# 模板：数据标准框架设计

> 使用时机：数据治理项目 Step 2（蓝图设计）第 4-6 天
> 输出物：《数据标准体系框架》+《第一批数据标准清单》

---

## 一、标准体系总体框架

```
数据标准体系
│
├── 第一层：基础标准（语言层）
│   ├── 业务术语标准 —— 统一业务语言，消除歧义
│   ├── 数据元标准 —— 字段级定义，最小数据单元
│   └── 编码规范 —— 命名规则、编码规则
│
├── 第二层：业务标准（业务层）
│   ├── 参考数据标准 —— 枚举值、代码表
│   ├── 主数据标准 —— 核心业务实体（客户/产品/机构）
│   └── 指标数据标准 —— 统一口径的业务指标
│
└── 第三层：技术标准（技术层）
    ├── 数据模型规范 —— 逻辑模型、物理模型设计规范
    ├── 接口规范 —— 系统间数据交互标准
    └── 交换格式规范 —— 文件格式、报文格式
```

**三层之间的关系**：

```
┌─────────────────────────────────────────────┐
│  基础标准（语言层）                            │
│  "我们说的是同一个意思"                        │
│  例："客户" = 与本公司发生业务关系的个人或机构   │
└─────────────────────────────────────────────┘
                    ↓ 引用
┌─────────────────────────────────────────────┐
│  业务标准（业务层）                            │
│  "这个业务对象应该长什么样"                     │
│  例：客户信息包含哪些字段，每个字段什么含义      │
└─────────────────────────────────────────────┘
                    ↓ 指导
┌─────────────────────────────────────────────┐
│  技术标准（技术层）                            │
│  "技术上怎么实现这个标准"                       │
│  例：客户姓名字段在数据库中用什么类型、多长      │
└─────────────────────────────────────────────┘
```

## 二、每层标准详细说明

### 2.1 基础标准（语言层）

**定位**：数据标准的"字典"，确保所有人用同一套语言说话。

---

#### （1）业务术语标准

**是什么**：对企业核心业务概念的统一定义。

**包含内容**：

| 要素 | 说明 | 示例 |
|:-----|:-----|:-----|
| 术语名称 | 标准中文名称 | 客户、借据、逾期天数 |
| 英文名称 | 标准英文名称 | Customer、Loan、DPD |
| 定义 | 用业务语言描述 | 客户：与本公司发生信贷业务关系的个人 |
| 适用范围 | 哪些场景使用这个术语 | 适用于核心系统、信贷系统、风控系统 |
| 相关术语 | 有关联的其他术语 | 客户 → 关联 → 借据、还款记录 |
| 禁止用法 | 明确不规范的说法 | "用户"不等于"客户"，客户必须发生业务关系 |

**术语标准模板**：

| 术语   | 英文       | 定义                  | 适用范围  | 同义词 | 禁用词   |
| :--- | :------- | :------------------ | :---- | :-- | :---- |
| 客户   | Customer | 与本公司发生信贷业务关系的个人     | 全公司   | 借款人 | 用户、访客 |
| 借据   | Loan     | 客户与公司签订的借款合同        | 信贷/核心 | 贷款  | 订单    |
| 逾期天数 | DPD      | 当前日期-到期还款日（不含到期日当天） | 风控/贷后 | -   | 滞纳天数  |

**常见问题**：
- ❌ "逾期"：有的说超过还款日就算，有的说超过宽限期才算
- ❌ "客户"：有的指注册用户，有的指发生交易的用户
- ❌ "余额"：有的说未还本金，有的说未还本息合计

---

#### （2）数据元标准

**是什么**：对单个数据字段的精确定义，是数据标准的最小单元。

**包含内容**：

| 属性 | 说明 | 示例 |
|:-----|:-----|:-----|
| 数据元名称 | 标准字段名 | customer_name |
| 中文名称 | 业务名称 | 客户姓名 |
| 定义 | 业务含义 | 客户在身份证上登记的姓名 |
| 数据类型 | 技术类型 | 字符串 |
| 数据长度 | 最大长度 | 50位 |
| 是否必填 | 必填/选填 | 是 |
| 取值范围 | 允许的值 | 与身份证件一致 |
| 质量标准 | 质量要求 | 非空率100% |
| Owner | 业务负责人 | 零售业务部总监 |

**数据元标准示例**：

| 数据元名称 | 中文名称 | 定义 | 数据类型 | 长度 | 必填 | 取值规则 | 质量标准 | Owner |
|:----------|:--------|:-----|:-------|:----:|:----:|:--------|:--------|:-----:|
| customer_id | 客户编码 | 客户唯一标识 | 字符串 | 20 | 是 | HB+渠道码+日期+序号 | 全局唯一 | 零售部 |
| customer_name | 客户姓名 | 身份证登记姓名 | 字符串 | 50 | 是 | 与证件一致 | 非空率100% | 零售部 |
| mobile | 手机号 | 客户预留手机号 | 字符串 | 11 | 是 | ^1[3-9]\d{9}$ | 格式合规率100% | 零售部 |
| cert_type | 证件类型 | 客户证件类型 | 枚举 | 2 | 是 | 01身份证/02护照 | 枚举合规率100% | 零售部 |
| cert_no | 证件号码 | 客户证件号码 | 字符串 | 18 | 是 | 身份证按GB 11643 | 校验通过率100% | 零售部 |

---

#### （3）编码规范

**是什么**：统一数据的命名规则和编码规则，让不同的人写出的代码/字段名一致。

**包含内容**：

| 规范类型 | 适用对象 | 规则示例 |
|:--------|:--------|:--------|
| 字段命名规范 | 数据库字段 | 小写下划线，如 customer_name |
| 表命名规范 | 数据库表 | t_ + 业务域 + 实体名，如 t_customer |
| 编码规则 | 业务编码 | 客户编码 = HB + 渠道码(1) + 日期(8) + 序号(6) |
| 枚举编码规则 | 枚举值 | 两位数字，如 01身份证、02护照 |
| 接口命名规范 | API接口 | /api/v1/{domain}/{action} |
| 文件命名规范 | 数据文件 | {系统}_{表名}_{日期}_{批次}.csv |

**字段命名规范示例**：

| 数据类型 | 命名规则 | 示例 |
|:--------|:--------|:-----|
| 字符串 | 名词，小写下划线 | customer_name, mobile |
| 日期 | 名词 + _date | birth_date, create_date |
| 日期时间 | 名词 + _time | create_time, update_time |
| 金额 | 名词 + _amount | loan_amount, repay_amount |
| 状态 | 名词 + _status | loan_status, repay_status |
| 编码 | 名词 + _code | customer_code, product_code |
| 标识 | 名词 + _id | customer_id, loan_id |
| 计数 | 名词 + _count | retry_count, fail_count |
| 标志位 | is_ + 形容词 | is_vip, is_deleted |

### 2.2 业务标准（业务层）

**定位**：直接指导业务操作和系统开发的标准，是数据标准的核心。

---

#### （1）参考数据标准

**是什么**：对枚举值、代码表的统一规范。

**典型参考数据**：

| 参考数据名称 | 说明 | 取值示例 |
|:------------|:-----|:--------|
| 证件类型 | 客户证件分类 | 01身份证、02护照、03军官证 |
| 性别 | 性别分类 | 0女、1男、9未知 |
| 学历 | 学历分类 | 01博士、02硕士、03本科... |
| 婚姻状况 | 婚姻状态 | 01未婚、02已婚、03离异... |
| 借据状态 | 借据生命周期状态 | 01正常、02逾期、03结清... |
| 还款方式 | 还款方式分类 | 1等额本息、2先息后本... |
| 产品类型 | 产品分类 | 01循环贷、02菁英贷、03乐居贷 |
| 渠道类型 | 客户来源渠道 | 1自营APP、2微信小程序... |

**参考数据标准模板**：

```
《证件类型参考数据标准》

一、标准编码
STD-REF-001

二、适用范围
全公司所有涉及客户证件类型的业务系统和数据平台

三、取值定义

| 标准编码 | 标准名称 | 说明 | 使用状态 | 生效日期 |
|:-------:|:--------|:-----|:-------:|:-------:|
| 01 | 居民身份证 | 中国大陆居民二代身份证 | 在用 | 2025-01-01 |
| 02 | 护照 | 中国护照或外国护照 | 在用 | 2025-01-01 |
| 03 | 军官证 | 中国人民解放军军官证 | 在用 | 2025-01-01 |
| 04 | 港澳居民来往内地通行证 | 港澳居民证 | 在用 | 2025-01-01 |
| 05 | 台湾居民来往大陆通行证 | 台湾居民证 | 在用 | 2025-01-01 |
| 99 | 其他 | 上述之外的证件类型 | 在用 | 2025-01-01 |

四、编码规则
- 格式：两位数字
- 新增编码：向数据治理办公室申请，由治理委员会审批
- 编码一旦发布，不可变更（只可新增或停用）

五、映射关系

| 标准编码 | 核心系统编码 | 信贷系统编码 | 报送系统编码 |
|:-------:|:----------:|:----------:|:----------:|
| 01 | 身份证 | ID | 101 |
| 02 | 护照 | PP | 102 |
| 03 | 军官证 | OG | 103 |
```

#### （2）主数据标准

**是什么**：对企业核心业务实体（客户、产品、机构等）的完整定义。

**典型主数据**：

| 主数据名称 | 说明 | 适用行业 |
|:----------|:-----|:--------|
| 客户主数据 | 客户的基本信息、联系信息、证件信息 | 通用 |
| 产品主数据 | 产品的基本信息、定价信息、状态信息 | 金融 |
| 机构主数据 | 组织架构、部门信息、岗位信息 | 通用 |
| 员工主数据 | 员工的基本信息、岗位信息、权限信息 | 通用 |
| 账户主数据 | 账户的开立信息、余额信息、状态信息 | 银行/消金 |
| 借据主数据 | 借款合同的基本信息、金额、期限 | 消金/银行 |

**主数据标准的核心内容**：

| 内容模块 | 说明 | 示例 |
|:--------|:-----|:-----|
| 术语定义 | 该主数据涉及的核心术语 | 客户、自然人客户、机构客户 |
| 编码规则 | 该主数据的唯一标识规则 | customer_id = HB + 渠道码 + 日期 + 序号 |
| 数据元标准 | 该主数据包含的所有字段定义 | 客户姓名、手机号、证件号等14个字段 |
| 质量标准 | 该主数据的质量要求 | 客户姓名非空率100%，手机号格式合规率100% |
| 生命周期 | 该主数据从产生到消亡的过程 | 注册→开户→在用→注销→归档 |
| Owner/Steward | 责任分工 | Owner：零售业务部总监 |

**主数据标准 vs 参考数据标准**：

| 对比项 | 主数据标准 | 参考数据标准 |
|:------|:----------|:------------|
| 定义对象 | 业务实体（如客户） | 枚举值（如证件类型） |
| 内容量 | 通常包含几十个字段 | 通常包含几到十几个取值 |
| 更新频率 | 随业务变化 | 相对稳定 |
| 影响范围 | 影响多个系统 | 影响字段的取值范围 |
| 制定难度 | 高（需要跨部门协调） | 中 |

#### （3）指标数据标准

**是什么**：对业务指标的统一口径定义，确保不同系统、不同报表的同一指标计算方式一致。

**典型业务指标**：

| 指标域 | 指标名称 | 常见口径分歧 |
|:------|:--------|:------------|
| 客户 | 客户总数 | 注册算客户？开户算客户？发生交易算客户？ |
| 客户 | 新增客户数 | 按注册日？按开户日？按首笔交易日？ |
| 信贷 | 贷款余额 | 本金？本息合计？含不含已逾期？ |
| 信贷 | 逾期率 | 按金额算？按笔数算？逾期几天算逾期？ |
| 风控 | 通过率 | 申请通过率？授信通过率？提款通过率？ |
| 运营 | 获客成本 | 含不含渠道返点？按注册算还是按开户算？ |

**指标数据标准模板**：

```
《业务指标数据标准 — 逾期率》

一、指标名称
逾期率

二、指标编码
IND-CREDIT-001

三、业务定义
在统计时点，逾期借据金额占全部借据金额的比例

四、计算公式
逾期率 = 逾期借据本金余额 / 全部借据本金余额 × 100%

五、分子定义
- 指标：逾期借据本金余额
- 定义：DPD > 0 的借据的未还本金合计
- DPD计算：DPD = 统计日期 - 到期还款日（不含到期日当天）

六、分母定义
- 指标：全部借据本金余额
- 定义：状态为"正常"或"逾期"的借据的未还本金合计
- 不含：已结清、已核销的借据

七、统计维度
- 时间维度：按日、按月、按季
- 产品维度：按产品类型、按渠道
- 客户维度：按客户评级、按地区

八、数据来源
- 主表：t_loan（借据表）
- 字段：loan_amount（放款金额）、repaid_principal（已还本金）

九、Owner
- 定义Owner：风控部总监（对口径负责）
- 技术Owner：数据管理部（对数据准确性负责）

十、变更记录
| 日期 | 版本 | 变更内容 | 变更人 | 审批人 |
|:-----|:----:|:--------|:------:|:------:|
| 2025-01-01 | V1.0 | 新建 | 王晓明 | 风控部总监 |
```

### 2.3 技术标准（技术层）

**定位**：指导技术实现的标准，确保不同系统的技术实现一致。

---

#### （1）数据模型规范

**包含内容**：

| 规范项 | 说明 | 示例 |
|:------|:-----|:-----|
| 命名规范 | 表名、字段名、索引名 | t_customer（客户表）、idx_cust_mobile（手机号索引） |
| 数据类型规范 | 各类型数据用什么数据库类型 | 金额用DECIMAL(18,2)，手机号用VARCHAR(11) |
| 主键规范 | 主键设计规则 | 所有表必须有主键，优先使用自增ID或UUID |
| 外键规范 | 外键设计规则 | 外键命名：fk_子表_父表_字段 |
| 分区规范 | 大表分区策略 | 交易流水表按月份分区 |
| 注释规范 | 表和字段必须有注释 | 注释用中文，说明业务含义 |
| 冗余规范 | 允许的数据冗余 | 核心字段允许适当冗余，提高查询效率 |

**示例 — 建表规范**：

```sql
-- ✅ 符合规范
CREATE TABLE t_customer (
    customer_id     VARCHAR(20)     NOT NULL    COMMENT '客户编码，HB+渠道码+日期+序号',
    customer_name   VARCHAR(50)     NOT NULL    COMMENT '客户姓名',
    cert_type       VARCHAR(2)      NOT NULL    COMMENT '证件类型：01身份证/02护照',
    cert_no         VARCHAR(18)     NOT NULL    COMMENT '证件号码',
    mobile          VARCHAR(11)     NOT NULL    COMMENT '手机号',
    create_time     DATETIME        NOT NULL    COMMENT '创建时间',
    update_time     DATETIME        NOT NULL    COMMENT '更新时间',
    PRIMARY KEY (customer_id),
    UNIQUE KEY uk_cert (cert_type, cert_no),
    INDEX idx_mobile (mobile)
) COMMENT='客户主数据表';

-- ❌ 不符合规范
CREATE TABLE customer (
    id          INT         NOT NULL,
    name        VARCHAR(255),
    phone       VARCHAR(20),
    created_at  TIMESTAMP
);
```

## 三、标准清单设计

### 3.1 标准清单模板

设计完框架后，输出《第一批数据标准清单》：

| 标准编号 | 标准名称 | 标准类型 | 适用范围 | 优先级 | 问题关联 | Owner | Steward | 计划发布时间 | 状态 |
|:-------:|:--------|:-------|:-------|:------:|:--------|:-----:|:-------:|:-----------:|:----:|

### 3.2 优先级评估方法

使用四维度评分法：

| 评估维度 | 权重 | 评分标准（1-5分） |
|:--------|:----:|:----------------|
| 使用频率 | 30% | 5=每天使用，1=很少使用 |
| 问题严重程度 | 30% | 5=导致监管处罚/业务损失，1=几乎无影响 |
| 监管要求 | 20% | 5=涉及EAST/1104等强制报送，1=无监管要求 |
| 技术可行性 | 20% | 5=现有系统可直接支持，1=需要系统重构 |

**计算示例**：

| 标准名称 | 使用频率(30%) | 问题严重(30%) | 监管要求(20%) | 技术可行(20%) | 加权得分 | 优先级 |
|:--------|:----------:|:----------:|:----------:|:----------:|:-------:|:------:|
| 客户主数据 | 5×0.3=1.5 | 5×0.3=1.5 | 4×0.2=0.8 | 4×0.2=0.8 | 4.6 | **P0** |
| 借据数据 | 5×0.3=1.5 | 5×0.3=1.5 | 5×0.2=1.0 | 3×0.2=0.6 | 4.6 | **P0** |
| 还款数据 | 4×0.3=1.2 | 3×0.3=0.9 | 4×0.2=0.8 | 4×0.2=0.8 | 3.7 | **P1** |
| 逾期率指标 | 3×0.3=0.9 | 4×0.3=1.2 | 2×0.2=0.4 | 5×0.2=1.0 | 3.5 | **P1** |
| 字段命名规范 | 2×0.3=0.6 | 2×0.3=0.6 | 1×0.2=0.2 | 5×0.2=1.0 | 2.4 | **P2** |

## 四、第一批标准选择原则

### 4.1 选择标准

**必须同时满足以下至少2条**：

| 标准 | 说明 |
|:-----|:-----|
| 高频使用 | 每天都在用的数据（客户、借据、交易） |
| 问题严重 | 数据质量问题多，已造成实际损失 |
| 监管要求 | 涉及EAST/1104/反洗钱等报送 |
| 跨系统使用 | 多个系统共享的数据 |
| 技术可行 | 现有系统条件下能落地 |

### 4.2 数量控制

| 阶段 | 标准数量 | 说明 |
|:-----|:-------:|:-----|
| 第一批 | 5-10个 | 聚焦核心，快速出成果 |
| 第二批 | 10-15个 | 扩展覆盖范围 |
| 第三批及以后 | 按需增加 | 持续完善 |

**第一批标准推荐结构**：

```
第一批标准（5-10个）
│
├── 基础标准（1-2个）
│   ├── 核心业务术语定义（可选）
│   └── 编码规范（必选，为后续标准打基础）
│
├── 业务标准（3-6个）
│   ├── 参考数据（1-2个）—— 先定枚举值
│   ├── 主数据（2-3个）—— 核心业务实体
│   └── 指标数据（0-1个）—— 争议最大的指标
│
└── 技术标准（1-2个）
    ├── 数据模型/字段命名规范（可选）
    └── 接口规范（如需系统改造）
```

## 五、设计原则详解

| 原则 | 说明 | 落地方法 |
|:-----|:-----|:--------|
| **先定领域，再定内容** | 不要一开始就写具体字段，先确定"需要哪些标准" | 用标准清单梳理，评审后再逐个制定 |
| **高频优先** | 每天都在用的数据先做 | 统计各表/字段的查询频率和使用范围 |
| **问题导向** | 质量问题严重的领域先做 | 结合调研报告中的TOP问题 |
| **监管驱动** | 涉及监管报送的数据必须优先 | EAST/1104涉及的字段必须纳入第一批 |
| **小步快跑** | 第一批控制在5-10个 | 宁少勿多，确保能按期完成 |
| **业务主导** | 标准由业务部门制定，IT配合 | Owner必须是业务方 |
| **可度量** | 每个标准必须有明确的质量检核规则 | 标准中必须包含质量要求 |

## 六、常见误区

| 误区 | 错误做法 | 正确做法 |
|:-----|:--------|:--------|
| 贪多求全 | 第一批就想定20个标准 | 第一批5-10个，先做出成果 |
| 理想主义 | 标准定义得非常完美，但系统实现不了 | 兼顾技术可行性，先定"能做到"的标准 |
| IT主导 | 由技术团队定义业务字段含义 | 业务Owner定义含义，IT评估技术可行性 |
| 忽略历史 | 新标准不考虑存量数据 | 标准中必须包含历史数据处置方案 |
| 忽视参考数据 | 只定主数据，不定枚举值 | 先定参考数据（枚举值），再定主数据 |
| 缺乏质量要求 | 标准只定义字段，不定义质量 | 每个标准必须包含质量检核规则 |
| 闭门造车 | 数据团队自己定标准，不征求业务意见 | 标准制定小组必须有业务代表 |

## 💡 关键技巧

| 技巧 | 说明 |
|:-----|:-----|
| 从参考数据入手 | 先统一枚举值（证件类型、借据状态），难度低、见效快 |
| 用Excel管理清单 | 标准清单用Excel维护，便于筛选、排序、跟踪状态 |
| 和业务痛点挂钩 | 每个标准都关联一个具体痛点，便于争取支持 |
| 预留扩展空间 | 编码规则预留位数，枚举值预留编码空间 |
| 参考行业标准 | 参考人行、银保监会的标准编码，减少自定义 |
| 每季度review | 标准框架不是一成不变的，每季度review是否需要调整 |

## ⚠️ 常见坑

| 坑 | 后果 | 如何避免 |
|:--|:-----|:--------|
| 标准范围定太大 | 制定不完，执行不了 | 聚焦核心领域，第一批5-10个 |
| 忽略现有系统 | 标准定好了但系统改不了 | 制定时让技术团队参与评审 |
| 业务部门不参与 | 标准不被认可，执行不下去 | 标准制定小组必须有业务代表 |
| 编码规则不合理 | 编码不够用或太长 | 预留扩展空间，参考行业惯例 |
| 没有版本管理 | 标准改了但下游不知道 | 每个标准必须有版本号和变更记录 |
| 标准之间冲突 | 不同标准的定义互相矛盾 | 建立标准评审机制，统一由治理办公室把关 |
