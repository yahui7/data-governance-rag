## 一、问题闭环流程

> **核心设计**：
> - Steward 不再是问题处理的"唯一责任人"，而是"业务侧参与者"
> - 数据治理团队作为"总台"统一受理和分派
> - 按问题类型路由到正确的人：业务规则 → Steward；系统缺陷 → IT开发

```
┌─────────────────────────────────────────────────────────────┐
│  ① 问题发现（自动化检核 / 业务反馈 / 监管通报）             │
│     • 系统自动触发 或 业务人员反馈                          │
│     • 数据治理团队统一接收（唯一入口）                      │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│  ② 问题受理（数据治理团队，1小时内）                        │
│     • 录入问题台账                                          │
│     • 技术初筛：定位系统 → 库 → 表 → 字段                   │
│     • 撰写"业务描述"（Steward能看懂的语言）                 │
│     • 判断问题类型：业务规则 / 系统缺陷 / 数据录入 / 外部数据 │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│  ③ 问题分派（数据治理团队）                                 │
│     ├─ 业务规则类（如：枚举值争议、业务含义不清）           │
│     │       → 分派给 Steward（附业务描述）                  │
│     │       → Steward 判断规则对错，给出业务处理意见        │
│     │                                                       │
│     ├─ 系统缺陷类（如：校验规则Bug、同步接口失败）          │
│     │       → 分派给 IT开发（附技术描述）                   │
│     │       → 抄送 Steward 知会                             │
│     │                                                       │
│     └─ 数据录入类（如：人工录入错误、历史数据问题）         │
│             → 分派给 Steward 确认责任方                     │
│             → Steward 协调业务补录或提交清洗需求            │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│  ④ 问题处理                                                 │
│     • Steward 不需要查数据库！                              │
│     • Steward 做的是：确认问题属实 → 判断业务规则 → 协调资源│
│     • IT开发做的是：排查系统 → 修复代码 → 执行清洗 → 自测  │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│  ⑤ 效果验证（数据治理团队）                                 │
│     • 重新跑检核规则，确认通过                              │
│     • 或人工抽检确认修复                                    │
│     • 更新台账状态                                          │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│  ⑥ 通知关闭                                                 │
│     • 通知 Steward / IT 确认关闭                            │
│     • 归档到问题台账                                        │
└─────────────────────────────────────────────────────────────┘
```

**为什么这样设计？**

| 设计点 | 解决的问题 |
|:-----|:---------|
| 治理团队统一受理 | Steward 不直接接触原始告警，避免被技术术语淹没 |
| 治理团队撰写"业务描述" | Steward 看到的是"APP开户手机号格式不对"，不是"t_customer.mobile RLIKE 不匹配" |
| 按类型分派 | 系统Bug让IT修，业务规则让Steward确认，各干各擅长的 |
| Steward 不查数据库 | Steward 是业务骨干，不是DBA，不应该要求他写SQL |

## 二、问题处理时效要求

**时效按"处理角色"分别设定**（ Steward 和 IT 开发有不同的时效要求）：

| 处理阶段 | 严重问题 | 警告问题 | 提示问题 |
|:--------|:-------:|:-------:|:-------:|
| **治理团队受理录入** | 1 小时内 | 4 小时内 | 1 个工作日内 |
| **Steward 响应（业务类）** | 4 小时内 | 1 个工作日内 | 无需响应 |
| **IT 开发响应（技术类）** | 4 小时内 | 1 个工作日内 | 无需响应 |
| **原因定位** | 1 个工作日内 | 3 个工作日内 | 无需定位 |
| **整改完成** | 3 个工作日内 | 5 个工作日内 | 无需整改 |
| **治理团队验证** | 1 个工作日内 | 1 个工作日内 | 1 个工作日内 |
| **超期升级** | 超期 1 天升级 Owner | 超期 3 天升级 Owner | 不升级 |

**各角色的 SLA 承诺**：

| 角色 | 承诺时效 | 说明 |
|:-----|:-------:|:-----|
| **数据治理团队** | 受理：1h；验证：1个工作日 | 7×24小时值班（严重问题） |
| **Steward** | 响应：4h；处理：3个工作日 | 工作日时间内（非24小时） |
| **IT 开发** | 响应：4h；修复：按排期 | 工作日时间，紧急可加班 |

## 三、问题升级机制

```
问题发现（数据治理团队统一受理）
    │
    ├── 一般问题（单字段、单系统）
    │   ├─ 业务规则类 → Steward 直接处理
    │   └─ 系统缺陷类 → IT 开发直接修复
    │
    ├── 复杂问题（多字段、跨系统、需要协调）
    │       └── 数据治理团队协调 Steward + IT 开发联合处理
    │       └── 协调不动 → 上报 Owner 拍板
    │
    ├── 严重问题（影响监管报送/业务运营/合规）
    │       └── Owner 上报数据治理委员会，委员会决策
    │
    └── 紧急问题（系统故障/数据泄露/大规模错误）
            └── 立即启动应急预案，通知 CRO/CDO
```

**升级触发条件**：

| 升级场景 | 触发条件 | 升级路径 | 决策人 |
|:--------|:--------|:--------|:-----|
| **Steward 未响应** | 严重问题超 4h / 警告超 1天 | 治理团队 → Owner | Owner |
| **IT 未响应** | 严重问题超 4h / 警告超 1天 | 治理团队 → IT 负责人 | IT 负责人 |
| **跨系统协调失败** | Steward 与 IT 互相推诿 | 治理团队 → Owner → 治理委员会 | 治理委员会 |
| **影响监管报送** | 报送截止前未修复 | 治理团队 → Owner → 治理委员会 | 治理委员会 |
| **批量数据错误** | 单问题影响 > 1000 条 | 立即升级 Owner | Owner |
| **系统故障** | 系统不可用 / 数据泄露 | 立即启动应急预案 | CRO/CDO |

## 四、问题台账

> ⚠️ **重要设计原则**：
> 1. **台账由数据治理团队统一管理**，不是由 Steward 维护
> 2. **每条问题必须同时有"业务描述"和"系统信息"**，Steward 看业务描述，IT 看系统信息
> 3. **问题处理按类型分派**：业务规则类 → Steward；系统缺陷类 → IT 开发

### 4.1 台账管理职责分工

| 角色 | 台账相关职责 | 说明 |
|:-----|:------------|:-----|
| **数据治理团队** | 统一录入、分派、状态更新、归档 | 问题管理的"总台"，唯一出口 |
| **Steward（业务侧）** | 接收分派、确认问题、给出业务意见 | 只看业务描述，不接触技术细节 |
| **IT 开发（技术侧）** | 接收分派、修复系统、执行清洗 | 看系统信息和技术描述 |
| **Owner** | 超期/重大问题升级处理 | 不处理日常台账操作 |

### 4.2 台账字段设计

| 字段 | 说明 | 填写人 | 示例 |
|:-----|:-----|:------:|:-----|
| **问题ID** | 唯一编号 Q-年份-序号 | 治理团队 | Q-2025-001 |
| **规则ID** | 触发检核的规则 | 治理团队 | Q011 |
| **系统名** | 问题所在的系统 | 治理团队 | APP开户系统 |
| **表名** | 数据库表名 | 治理团队 | t_customer |
| **字段名** | 数据库字段名 | 治理团队 | mobile |
| **业务对象** | Steward 能看懂的描述 | 治理团队 | 客户手机号 |
| **问题来源** | 如何发现的 | 治理团队 | 自动化检核 |
| **问题类型** | 业务规则/系统缺陷/数据录入/外部数据 | 治理团队 | 系统缺陷 |
| **业务描述** | 用业务语言描述问题 | 治理团队 | APP开户时允许输入带横线的手机号（如 138-0013-8000），导致格式不合规 |
| **技术描述** | 用技术语言描述问题 | 治理团队 | 字段 mobile 有 45 条记录不匹配正则 ^1[3-9]\d{9}$ |

| **主责角色** | 谁主责处理 | 治理团队 | IT开发 |
| **处理人** | 具体人名 | 治理团队 | 李工（IT） |
| **抄送Steward** | 知会的 Steward | 治理团队 | 张工 |

| **整改方案** | 具体修复措施 | 处理人 | ①修复APP校验正则 ②清洗历史45条 |
| **处理时间** | 实际处理完成时间 | 治理团队 | 2025-08-02 |
| **验证结果** | 通过/不通过 | 治理团队 | 通过 |
| **验证方式** | 如何验证的 | 治理团队 | 重新跑批+抽检10条 |

## 五、Steward 如何处理数据问题（操作指南）

> **核心原则**：Steward 不需要懂数据库、不需要写 SQL、不需要看表结构。
> Steward 的职责是**业务视角的问题确认和协调**。

### Steward 收到问题后做什么？

**第 1 步：看"业务描述"，确认问题是否属实**

治理团队发来的问题长这样：

```
【问题通知】
问题ID：Q-2025-002
业务对象：客户身份证
业务描述：核心系统发现12条客户身份证校验不通过
问题类型：数据录入
需要您确认：
  1. 这12条记录是否确实是老客户的15位身份证未升位？
  2. 升位后是否需要联系客户确认？
  3. 是否有批量处理的业务流程？
截止时间：2025-08-01 18:00
```

Steward 要做的：
- ✅ 打开业务系统（不是数据库！），搜索这几个客户的记录
- ✅ 核对身份证信息是否确实有问题
- ✅ 确认是公司录入错误还是客户提供的就是错的
- ❌ 不需要写 SQL 查数据库
- ❌ 不需要看 `t_customer.cert_no` 这种技术字段

**第 2 步：判断问题类型，给出处理意见**

| 问题类型 | Steward 的判断要点 | Steward 的处理动作 |
|:--------|:------------------|:-----------------|
| **业务规则争议** | "这个字段的业务规则到底是什么？" | 确认规则 → 通知相关方 → 规则变更走标准变更流程 |
| **数据录入错误** | "是人的操作问题还是系统问题？" | 确认错误来源 → 安排补录 → 提出防错建议 |
| **外部数据问题** | "是合作方给的数据有问题吗？" | 联系合作方 → 确认数据标准 → 约定修复方案 |
| **系统缺陷** | "这确实是系统Bug，不是规则问题" | 确认属实 → 告知治理团队转 IT 开发 → 关注修复进度 |

**第 3 步：协调资源，推动处理**

Steward 可以协调的人：
- 本部门业务人员（补录数据、确认业务规则）
- 外部合作方（数据源问题）
- 向 Owner 汇报（需要部门资源支持时）

Steward 不可以也不应该做的事：
- ❌ 直接修改数据库
- ❌ 写 SQL 查询
- ❌ 自己部署修复代码
- ❌ 维护问题台账

**第 4 步：确认关闭**

治理团队验证通过后，会通知 Steward：

```
【问题关闭通知】
问题ID：Q-2025-002 已修复并通过验证
验证方式：重新跑批 + 抽检5条
Steward 确认：如确认无误请回复"确认关闭"
```

Steward 回复"确认关闭"即可。

### 典型场景处理示例

**场景 1：手机号格式不合规（系统缺陷类）**

```
问题：APP开户时允许输入带横线的手机号

Steward 的操作：
1. 打开 APP，尝试输入 138-0013-8000，确实能提交
2. 确认：这是系统前端校验的Bug，不是业务规则问题
3. 回复治理团队："确认是系统问题，请转 IT 修复。建议前端增加格式校验。"
4. 后续关注 IT 修复进度
```

**场景 2：证件有效期过期（外部数据类）**

```
问题：68条客户证件已过期

Steward 的操作：
1. 打开 CRM 系统，查看其中几条记录，确实显示证件过期
2. 确认：客户证件到期是正常的，需要通知客户更新
3. 回复治理团队："确认属实。属于正常业务场景，我会安排客服短信通知客户更新证件。预计1周内处理完。"
4. 协调客服团队发送通知
5. 1周后向治理团队反馈处理结果
```

**场景 3：产品类型编码不一致（业务规则类）**

```
问题：核心系统和信贷系统对同一产品的类型编码不一致

Steward 的操作：
1. 打开两个系统，对比同一产品的类型编码
2. 确认：核心系统用"01"，信贷系统用"1"，确实不一致
3. 判断：应该以核心系统为准（公司业务定义的核心系统为准）
4. 回复治理团队："确认不一致。业务规则：以核心系统编码为准。请通知信贷系统修改映射关系。"
5. 在部门内同步这一规则，避免后续再次出现
```

## 六、根因分析模板

每个严重问题必须做根因分析，使用 **5Why 分析法**：

**示例：Q-2025-001 手机号格式不合规**

| Why | 答案 |
|:----|:-----|
| **Why 1**：为什么会出现 45 条手机号格式不合规？ | APP 开户时允许输入带横线的手机号（如 138-0013-8000） |
| **Why 2**：为什么 APP 允许输入带横线的手机号？ | APP 前端校验规则只检查了长度，没检查格式 |
| **Why 3**：为什么前端校验规则不完整？ | 开发时只参考了旧标准，新标准的正则校验规则未同步到 APP |
| **Why 4**：为什么新标准没同步到 APP？ | 标准发布后没有建立"标准变更→系统同步"的机制 |
| **Why 5**：为什么没有建立同步机制？ | 缺乏标准变更管理流程 |
| **根因** | 缺乏标准变更管理流程，导致标准发布后下游系统未及时同步 |
| **预防措施** | 建立标准变更通知机制：标准发布后 24 小时内通知所有相关系统 |
