# 客户信息数据标准 V1.0

**标准编号**：STD-001
**标准类型**：主数据标准
**适用范围**：全公司所有涉及客户信息的业务系统和数据平台
**发布日期**：2025 年 6 月 30 日
**生效日期**：2025 年 7 月 1 日
**版本**：V1.0
**编制部门**：数据治理办公室

---

## 一、标准目的

### 1.1 背景

当前公司客户信息分散在核心系统、信贷系统、风控系统、APP 等多个系统中，存在以下问题：

| 问题 | 具体表现 | 影响 |
|:-----|:--------|:-----|
| 客户编码不统一 | 同一客户在核心系统编号为 10012345，在信贷系统为 CT-87654 | 客户画像无法关联，多头借贷识别率低 |
| 手机号格式混乱 | 同一客户手机号在各系统格式不同：13800138000 / 138-0013-8000 / +8613800138000 | 设备指纹关联失败，风控策略失效 |
| 证件类型编码不一致 | 核心系统用"身份证"，信贷系统用"01"，报送系统用"101" | EAST 报送映射错误，被监管点名 |
| 字段定义模糊 | "客户姓名"是否包含生僻字、是否允许空格，各系统理解不同 | 监管报送与客户实际信息不一致 |
| 缺少质量要求 | 客户手机号无格式校验，证件有效期无到期预警 | 反洗钱数据质量差，合规风险高 |

### 1.2 目的

1. **统一客户信息的业务定义**：确保全公司对"客户""客户姓名""证件类型"等概念的理解一致
2. **统一客户信息的格式规范**：确保客户信息在各系统中的格式一致，可直接关联
3. **明确客户信息的质量要求**：确保客户信息满足业务运营和监管报送的最低质量要求
4. **明确责任分工**：确保每个字段都有明确的 Owner 和 Steward

### 1.3 预期收益

| 收益类型 | 具体指标 | 目标 |
|:--------|:--------|:-----|
| 质量提升 | 客户手机号格式合规率 | 从 89.5% 提升到 100% |
| 质量提升 | 客户证件信息完整率 | 从 88% 提升到 100% |
| 效率提升 | 客户画像准确率 | 从 68% 提升到 95% |
| 合规提升 | EAST 报送客户信息错误率 | 从 8.5% 降到 0.2% |
| 效率提升 | 跨系统客户信息核对人工耗时 | 降低 80% |

## 二、适用范围

### 2.1 适用系统

本标准适用于以下所有涉及客户信息采集、存储、使用、传输的系统：

| 系统名称 | 系统类型 | 涉及客户信息的功能 |
|:--------|:--------|:-----------------|
| 核心系统 | 业务系统 | 客户开户、信息管理、客户查询 |
| 信贷系统 | 业务系统 | 贷款申请、合同签订、客户信息录入 |
| 风控决策引擎 | 业务系统 | 客户评级、授信审批、反欺诈 |
| APP（小鱼福卡） | 渠道系统 | 客户注册、开户、信息维护 |
| 微信小程序 | 渠道系统 | 客户注册、开户、信息维护 |
| CRM 系统 | 管理系统 | 客户管理、营销活动、客户服务 |
| 数据仓库 | 数据平台 | 客户数据分析、客户画像 |
| EAST 报送平台 | 监管报送 | 客户信息监管报送 |
| 1104 报送平台 | 监管报送 | 客户信息监管报送 |
| 征信报送系统 | 外部对接 | 征信信息报送 |

### 2.2 适用场景

| 场景 | 说明 |
|:-----|:-----|
| 新建系统 | 2025 年 7 月 1 日后新建或重构的系统，必须严格按本标准执行 |
| 已有系统改造 | 按《落标实施计划》分批改造，详见第八节 |
| 外部数据接入 | 从合作方、三方数据源接入的客户信息，按本标准进行清洗和映射 |
| 数据交换 | 系统间传输客户信息时，必须按本标准格式传输 |

### 2.3 不适用场景

| 场景 | 说明 |
|:-----|:-----|
| 匿名化数据 | 已脱敏/匿名化后的客户信息，不受本标准约束 |
| 测试环境 | 测试环境的客户信息可参考本标准，不作强制要求 |
| 历史归档数据 | 已归档超过 5 年的历史客户数据，暂不要求改造 |

## 三、术语定义

### 3.1 核心术语

| 术语 | 英文 | 定义 | 适用范围 | 禁用词 |
|:-----|:-----|:-----|:---------|:-------|
| **客户** | Customer | 与本公司发生信贷业务关系的**个人**，包括已注册未开户、已开户在用、已结清/注销的客户 | 全公司 | 用户（注册用户不一定是客户）、借款人（过于狭窄） |
| **自然人客户** | Individual Customer | 以个人身份办理业务的客户，区别于机构客户 | 全公司 | 个人（口语化） |
| **机构客户** | Corporate Customer | 以企业、组织身份办理业务的客户，如小微企业主以企业名义借款 | 全公司 | 企业客户（不含其他组织） |
| **潜在客户** | Potential Customer | 已注册但尚未完成开户流程的客户 | 营销/运营 | 注册用户（应与"客户"区分） |
| **有效客户** | Active Customer | 当前存在未结清借据的客户 | 信贷/风控 | 在贷客户（仅指有借据的，不含信用卡等） |
| **注销客户** | Closed Customer | 已主动申请注销或被动注销的客户，不再提供服务 | 全公司 | 删除客户（客户数据不能物理删除） |

### 3.2 与"客户"相关的易混淆概念

```
访客（Visitor）
  └── 仅浏览，未注册
      └── 注册用户（Registered User）
          └── 潜在客户（Potential Customer） — 已注册，但未开户
              └── 客户（Customer） — 已完成开户
                  ├── 有效客户（Active Customer） — 有未结清借据
                  ├── 休眠客户（Dormant Customer） — 无借据，但账户有效
                  └── 注销客户（Closed Customer） — 已注销
```

> **关键区分**：本标准中的"客户"特指已完成开户流程的、与本公司发生业务关系的个人，不包括仅注册未开户的"潜在客户"。

### 4.2 核心字段详细说明

以下对业务最关键、最容易出问题的字段进行详细说明。

---

#### 字段 1：customer_id（客户编码）

| 属性 | 内容 |
|:-----|:-----|
| **业务定义** | 客户在全公司的唯一标识，一旦生成永不变更，客户注销后也不回收复用 |
| **编码规则** | HB + 渠道码(1位) + 开户日期(YYYYMMDD, 8位) + 当日序号(6位) |
| **示例** | HB120250301000001 = 湖北消金、自营 APP、2025-03-01、当日第 1 位客户 |
| **数据类型** | VARCHAR(20) |
| **是否必填** | 是 |
| **生成时机** | 客户完成开户流程时自动生成 |
| **变更规则** | **不可变更**。如发生证件信息变更，customer_id 保持不变，仅更新 cert_no 等关联字段 |
| **质量标准** | 全局唯一、非空率 100%、格式合规率 100% |
| **Owner** | 零售业务部总监 |

**与其他系统编码的关系**：

| 系统 | 系统内部编码 | 与客户编码的关系 |
|:-----|:-----------|:----------------|
| 核心系统 | cust_no | 保留内部编码，新增 customer_id 字段，建立映射关系 |
| 信贷系统 | credit_cust_id | 保留内部编码，新增 customer_id 字段，建立映射关系 |
| 风控系统 | risk_user_id | 保留内部编码，新增 customer_id 字段，建立映射关系 |
| APP | app_user_id | 保留内部编码，新增 customer_id 字段，建立映射关系 |
| EAST 报送 | east_cust_id | 直接使用 customer_id |

---

#### 字段 2：customer_name（客户姓名）

| 属性 | 内容 |
|:-----|:-----|
| **业务定义** | 客户在法定证件（身份证/护照/军官证）上登记的姓名 |
| **数据类型** | VARCHAR(50) |
| **是否必填** | 是 |
| **取值规则** | ① 必须与证件上登记的姓名完全一致<br>② 去除首尾空格和不可见字符<br>③ 允许生僻字，系统必须支持 Unicode 生僻字存储<br>④ 少数民族姓名中的"·"（U+00B7）保留，如"买买提·艾力"<br>⑤ 不允许使用英文字母（护照除外） |
| **示例** | ✅ "张三"、"买买提·艾力"、"欧阳雪梅"<br>❌ " 张三 "（含首尾空格）、"张 三"（中间有空格）、"Zhang San" |
| **变更规则** | 客户申请姓名变更时，需提供公安机关出具的变更证明，由 Steward 审核后变更 |
| **质量标准** | 非空率 100%、首尾空格率 0%、格式合规率 100% |
| **Owner** | 零售业务部总监 |

**历史数据清洗规则**：

| 问题类型 | 问题示例 | 清洗规则 | 清洗后 |
|:--------|:--------|:--------|:------|
| 首尾空格 | " 张三 " | 去除首尾空格 | "张三" |
| 不可见字符 | "张三\n" | 去除不可见字符 | "张三" |
| 全角空格 | "　张三" | 替换为普通空格后去除 | "张三" |
| 简繁不一致 | "張三"（台湾身份证） | 保留原样，不做转换 | "張三" |

**证件类型编码表**：

## 五、编码规则

### 5.1 客户编码（customer_id）生成规则

**编码结构**：`HB` + `渠道码(1位)` + `开户日期(YYYYMMDD, 8位)` + `当日序号(6位)`

**总长度**：2 + 1 + 8 + 6 = 17 位（预留 3 位扩展，数据库字段长度设为 20）

**编码示例**：

| 编码 | 拆解 | 含义 |
|:-----|:-----|:-----|
| HB120250301000001 | HB / 1 / 20250301 / 000001 | 湖北消金、自营 APP、2025-03-01、第 1 位客户 |
| HB220250301000123 | HB / 2 / 20250301 / 000123 | 湖北消金、微信小程序、2025-03-01、第 123 位客户 |
| HB520250302999999 | HB / 5 / 20250302 / 999999 | 湖北消金、合作渠道、2025-03-02、第 999999 位客户 |

**生成规则**：

1. 客户完成开户流程（含实名认证）后，由核心系统自动生成
2. 按开户日期和渠道分别计数，每个渠道每天从 000001 开始递增
3. 序号达到 999999 时，系统自动预警，由数据治理办公室评估是否扩展位数
4. **严禁手动修改 customer_id**，一经生成永不变更

**并发控制**：
- 使用数据库序列号或分布式 ID 生成器，确保高并发下不重复
- 生成 customer_id 后，需在 500ms 内完成数据库写入，超时则重新生成

| Q025 | 证件号一致性 | 同一 customer_id 在各系统的 cert_no+cert_type 一致 | 100% | 严重 |
| Q026 | 风险等级一致性 | 同一 customer_id 在风控系统和核心系统的 risk_level 一致 | 100% | 警告 |

## 八、Owner 与 Steward

### 8.1 责任分工

| 角色 | 人员 | 职责 |
|:-----|:-----|:-----|
| **Owner** | 零售业务部总监 | ① 对客户信息标准的业务定义负最终责任<br>② 审批标准变更申请<br>③ 协调跨部门争议<br>④ 将客户数据质量纳入部门 KPI |
| **Steward** | 零售业务部数据管理员（张工） | ① 日常维护客户信息标准<br>② 处理客户信息质量问题<br>③ 审核客户信息变更申请<br>④ 定期向 Owner 汇报质量状况<br>⑤ 作为业务咨询接口，解答各方对客户信息的疑问 |
| **技术 Custodian** | 信息技术部数据架构师（李工） | ① 负责客户信息的技术存储和安全<br>② 评估标准变更的技术可行性<br>③ 执行系统改造和数据清洗<br>④ 保障客户信息的备份和恢复 |
| **质量监控** | 数据治理办公室（王晓明） | ① 配置和维护质量检核规则<br>② 监控客户信息质量指标<br>③ 发现质量问题并分发处理<br>④ 定期发布质量报告 |

### 8.2 问题升级路径

```
发现问题
    │
    ▼
Steward（张工）2 小时内响应
    │
    ├── 简单问题 → Steward 直接处理 → 闭环
    │
    └── 复杂问题/跨部门问题 → 上报 Owner（零售业务部总监）
            │
            ├── Owner 可决策 → Owner 决策 → Steward 执行 → 闭环
            │
            └── Owner 无法决策 → 上报数据治理委员会
                    │
                    ▼
                治理委员会决策 → 各方执行 → 治理办公室验证 → 闭环
```

## 九、变更管理

### 9.1 变更类型

| 变更类型 | 说明 | 示例 |
|:--------|:-----|:-----|
| **字段新增** | 新增数据元 | 新增 "email" 字段 |
| **字段修改** | 修改字段定义、类型、长度、取值规则 | 将 mobile 长度从 11 改为 20 |
| **字段停用** | 停止使用某个字段 | 停用 rarely_used_field |
| **编码变更** | 修改枚举值编码 | 新增证件类型 "07=士兵证" |
| **质量标准变更** | 修改质量检核规则或目标值 | 将 mobile 格式合规率从 100% 改为 99% |
| **Owner 变更** | 变更字段的 Owner 或 Steward | 因组织架构调整变更 Owner |

### 9.2 变更流程

```
变更申请 → 影响评估 → 评审 → 审批 → 发布 → 实施 → 验证
```

| 步骤 | 责任人 | 内容 | 时限 |
|:-----|:------|:-----|:----:|
| 变更申请 | Steward | 填写《数据标准变更申请表》，说明变更原因、内容、影响范围 | - |
| 影响评估 | 数据治理办公室 | 评估变更对下游系统、报表、接口的影响 | 2 个工作日 |
| 评审 | 标准制定小组 | 业务代表+技术代表共同评审 | 3 个工作日 |
| 审批 | Owner/治理委员会 | 一般变更由 Owner 审批；重大变更由治理委员会审批 | 2 个工作日 |
| 发布 | 数据治理办公室 | 更新标准文档，发布变更通知 | 1 个工作日 |
| 实施 | 信息技术部 | 按《落标实施计划》执行系统改造 | 按变更计划 |
| 验证 | 数据治理办公室 | 验证变更是否按要求实施，质量是否达标 | 实施后 1 周 |

### 9.3 变更分级

| 变更级别 | 判断标准 | 审批人 | 提前通知时间 |
|:--------|:--------|:------|:-----------:|
| **重大变更** | 涉及 customer_id 编码规则变更、字段删除、质量标准大幅降低 | 数据治理委员会 | 提前 4 周 |
| **一般变更** | 新增字段、新增枚举值、Owner 变更 | Owner | 提前 2 周 |
| **微小变更** | 字段注释修改、文档勘误 | Steward | 提前 1 周 |

### 9.4 紧急变更

如遇监管要求、重大安全事件等紧急情况，可启动紧急变更流程：

1. Steward 口头向 Owner 申请
2. Owner 口头同意后，Steward 先执行变更
3. 变更完成后 24 小时内补交书面变更申请
4. 数据治理办公室事后审核

## 附录 B：标准起草指南

### B.1 起草流程

```
Step 1: 收集需求
  └── 访谈业务部门，了解现有客户信息的使用场景和痛点
  └── 收集各系统现有的客户信息字段定义
  └── 收集监管对客户信息的报送要求（EAST/1104/征信）

Step 2: 编写初稿
  └── 按本模板结构编写标准文档
  └── 重点完成"数据元标准"章节（核心内容）
  └── 每个字段必须有明确的业务定义、取值规则、质量标准

Step 3: 内部评审
  └── 数据治理团队内部评审
  └── 检查：字段是否完整、定义是否清晰、规则是否可执行

Step 4: 跨部门评审
  └── 召集业务代表（Owner/Steward）、技术代表、数据代表
  └── 逐条讨论每个字段的定义和规则
  └── 记录评审意见和修改记录

Step 5: 修改定稿
  └── 根据评审意见修改
  └── 提交 Owner 审批签字

Step 6: 正式发布
  └── 发布标准文档
  └── 通知所有相关方
  └── 纳入元数据管理平台
```

### B.2 起草要点

| 要点 | 说明 |
|:-----|:-----|
| 用业务语言 | 不要用技术术语（如 VARCHAR、INT），用业务语言描述（如"字符串""整数"） |
| 定义要精确 | 避免模糊描述，如"尽量完整"→改为"非空率 100%" |
| 规则要可执行 | 每个规则都要能转化为 SQL 或代码，如手机号正则 `^1[3-9]\d{9}$` |
| 考虑历史数据 | 标准不能只面向新数据，必须包含存量数据的处置方案 |
| 关联监管要求 | 涉及监管报送的字段，必须满足监管口径要求 |
| 预留扩展空间 | 编码规则预留位数，枚举值预留编码空间 |
| 明确责任 | 每个字段必须有 Owner，整个标准必须有 Steward |

### B.3 质量检核规则设计指南

| 字段类型 | 推荐检核维度 | 示例 |
|:--------|:------------|:-----|
| 主键/编码 | 完整性、唯一性、格式合规 | customer_id 非空、唯一、格式匹配 |
| 姓名/地址 | 完整性、准确性（无异常字符） | customer_name 非空、无首尾空格 |
| 证件号 | 完整性、准确性（校验算法） | cert_no 非空、身份证模 11 校验 |
| 手机号 | 完整性、准确性（正则） | mobile 非空、正则匹配 |
| 枚举值 | 完整性、枚举合规 | cert_type 非空、取值在枚举范围内 |
| 日期 | 完整性、有效性（不过期/不晚于今天） | cert_valid_date > 当前日期 |
| 金额 | 完整性、范围（>0） | loan_amount > 0 |
